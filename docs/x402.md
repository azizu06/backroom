# Payables pays an invoice using x402 testnet

Refs #7. Coinbase Payment Agents stretch for Backroom, Cal Hacks 13.0.

The Payables seat paid an approved **Acme Supply demo invoice for 0.01 testnet
USDC** using x402 v2 on **Base Sepolia only**. Code decides whether to pay;
models do not hold keys, choose networks, approve exceptions, or sign payments.
Nessie remains the default rail. Every x402 endpoint response, result, CLI
receipt and payment audit identifies the rail as **x402 testnet**.

## Coinbase Payment Agents

### Summary

Backroom is a Payment Agent for a small business budget. Its Coinbase integration
uses the official `@coinbase/cdp-sdk` server wallet API (`getOrCreateAccount`,
`getAccount`, `requestFaucet`) plus maintained x402 v2 SDKs. The named EVM server
account is **`backroom-payables`**. Its SDK account is viem compatible; x402's
`toClientEvmSigner(account)` bridges it into the existing `ExactEvmScheme` without
exporting a private key. This is the same bridge used by CDP's
[`fromCdpEvmAccount` example](https://github.com/coinbase/cdp-sdk/blob/main/examples/typescript/x402/clients/x402DevMigration.ts),
without importing its unrelated optional x402/Solana peers.
Next.js keeps `@coinbase/cdp-sdk` in `serverExternalPackages`: Node loads it only
on the server, and Turbopack does not require unused optional Solana modules.
Deploying this dependency change requires `pnpm install --frozen-lockfile`.

### Architecture and controls

```text
Payables in-process MCP (Claude Agent SDK createSdkMcpServer/tool)
  coinbase_wallet_balance → getAccount → Base Sepolia USDC balance (read-only)
  coinbase_x402_pay → trusted case → PayablesSeat → policy/master/PO/dedupe
    → validated x402 challenge → named CDP wallet → fresh policy → signature
    → facilitator → exact Transfer + AuthorizationUsed → audit receipt
```

The tools register through the existing role-tool adapter in `agents/tools.ts`;
there is no second dispatcher or runtime. Both take an empty strict input schema.
The payment tool only accepts the trusted case's one-cent invoice, requires an
x402-configured seat and `X402_LIVE=1`, and shares `request_payment` deduplication.
It does not accept money, recipient, chain, approval, or invoice arguments.
Normal Nessie seats return **UNAVAILABLE**. The read tool never creates, funds,
signs or pays. Provider errors return sanitized UNAVAILABLE/held results; no
credential, signature or raw provider body is exposed to the model or browser.

### Working example and setup on another developer's Mac

1. In [CDP Portal](https://portal.cdp.coinbase.com), create a Secret API key and
   generate a Wallet Secret for server wallets. Follow the official
   [API-key wallet quickstart](https://docs.cdp.coinbase.com/wallets/quickstart/api-key-auth).
2. In macOS Keychain Access, add generic password items with service names:
   - `backroom-cdp-api-key`: password is the downloaded JSON `{ "id": "…", "privateKey": "…" }`.
   - `backroom-cdp-wallet-secret`: password is the raw Wallet Secret.
   Use Keychain Access to avoid putting credentials in shell history or argv.
   The host reads them at runtime with `security find-generic-password -w`.
   The API-key loader accepts raw JSON and macOS's hex-encoded JSON output.
   Never place these in `.env`, logs, Git, browser storage or the GX10.
3. Run `pnpm install` and `pnpm --filter @backroom/orchestrator x402:wallet` for
   the existing demo vendor's Keychain wallet. Start the app with `X402_LIVE=1`
   to enable the operator's existing testnet button. `PAYMENT_RAIL=x402` selects
   the x402 adapter for other Payables seats; it is not required for the console's
   explicitly selected x402 run. Give agent bootstrap a real x402 `PayablesSeat`
   (including its read-only `paymentRail` getter), not a Nessie wrapper.
4. On first payment setup, `getOrCreateAccount({name:'backroom-payables'})`
   loads/creates the same account in that CDP project. Code reads the fixed
   Base Sepolia USDC contract. Below **0.05 test USDC**, it requests the CDP
   faucet with `{network:'base-sepolia', token:'usdc'}`, waits for a successful
   receipt, and rechecks the threshold. Faucet/provider failure is UNAVAILABLE;
   no payment is signed. No ETH is required by the payer for x402 settlement.

CDP is preferred whenever both Keychain items exist. Missing/inaccessible or
malformed credentials fail closed. To retain the old direct-key demo fallback
when the CDP items are absent, explicitly set `X402_ALLOW_DIRECT_KEY=1`; that path
uses the existing `backroom-x402-testnet-key` payer and needs test USDC from
Circle's faucet. A CDP provider/faucet error never silently switches wallets.
The receipt adds only the wallet label and public payer address; the settlement
audit records both too.

### One-shot CDP testnet proof

**Current live result: PAID through the public x402 facilitator.** On October 25,
2026, the named CDP server wallet `backroom-payables` at
`0x07d9Ba3B202Aa079DBFa8D8eD52c4F75DC551DB3` paid the approved Acme Supply
invoice for **0.01 Base Sepolia test USDC** using the actual
`mcp__backroom__coinbase_x402_pay` tool handler.

[Base Sepolia transaction](https://sepolia.basescan.org/tx/0xff9d026523db51c01609f70c9a59fa4668a5bf42162c2b8a108f46f1f5dc62c4)
settled in block **50084970**. The [sanitized CDP receipt](evidence/x402/cdp-live.json)
records policy ALLOW, successful facilitator verification/settlement and a valid
nine-entry audit chain. An [independent read-only confirmation](evidence/x402/cdp-confirmation.json)
checks chain 84532, transaction success, the exact 10,000-unit USDC Transfer from
the CDP payer to the approved vendor, and its matching AuthorizationUsed nonce.
The facilitator sponsored settlement gas; **self-relay was not used**.

The successful run used a **600-second authorization window**. The operator's
explicit testnet console also selects this window; the generic adapter retains
its default 120-second maximum unless trusted bootstrap explicitly selects the
600-second cap. The CLI selects the longer window with
`X402_AUTHORIZATION_SECONDS=600`. This changes no invoice amount, recipient,
asset, network, policy, once-per-process or chain-confirmation check.

Earlier [held](evidence/x402/cdp-held.json) and
[diagnostic held](evidence/x402/cdp-diagnostic-held.json) attempts returned
`invalid_exact_evm_transaction_failed` without a transaction hash. Their
[reconciliation](evidence/x402/cdp-diagnostic-reconciliation.json) found unused
authorizations. The [read-only checks](evidence/x402/cdp-diagnostic.json) and
[unsent eth_call simulation](evidence/x402/cdp-ethcall.json) confirmed the CDP EOA,
USDC domain and successful contract simulation; the failed authorization still
had 59 seconds remaining at settlement. The later success with a longer window
does not establish the cause of those earlier failures. Each authorized new run
used a fresh nonce and exclusive journal; no declined authorization was replayed.
New runs retain only sanitized reason codes and public authorization metadata,
never signatures or raw provider details.

After tests and typecheck pass, run this once with a new absolute journal path
outside the repository:

```sh
X402_LIVE=1 PAYMENT_RAIL=x402 X402_AUTHORIZATION_SECONDS=600 pnpm --filter @backroom/orchestrator x402:cdp-live /absolute/private-task-dir/cdp-live.json
```

This invokes the real `mcp__backroom__coinbase_x402_pay` SDK tool handler
deterministically, without a paid model call. It uses the approved Acme Supply
one-cent demo invoice, real CDP signing, public x402 testnet settlement and both
on-chain receipt checks. The exclusive journal is written before setup/signing;
rerunning the same path refuses payment. Never delete a journal after an
uncertain result to retry. Public output includes the wallet, hash, BaseScan
link and hash-chained audit. The old direct-wallet historical proof below is
separate and remains immutable.

Limits: **Base Sepolia `eip155:84532` and its test USDC only**. Live signing is
capped at **one cent, once per process across console/MCP/default adapter**;
an uncertain signature consumes that allowance too. The repository and vendor
dedupe remain single-process demo storage; a restart is not durable spending
authority. Use the exclusive CLI journal for evidence, and reconcile before
any deliberately new run. Keys remain Mac-only; this change does not configure
or deploy the live host. No hosted Coinbase for Agents MCP/OAuth session, real
money, mainnet transaction or autonomous-model payment was exercised by this CLI.

### Builder feedback

The hosted Coinbase for Agents MCP was our adoption blocker: it requires a
retail Coinbase OAuth login, an allowlisted client, and retail USDC on Base
mainnet, with no Base Sepolia path for our sandboxed finance agent. We used CDP
server wallets plus x402 instead, preserving policy-controlled, invoice-bound
signing and testnet-only proof. The one missing capability we want is **a testnet
mode with invoice-bound spend policies for the Agents MCP**. That would let a
small-business budget agent demonstrate the same integration safely without a
retail-funded mainnet account. Our two tools are Backroom's in-process MCP tools,
not a claim that we connected the hosted Coinbase for Agents MCP.

## Architecture and contracts

```text
PayablesSeat.process(invoice, trusted envelope)
  vendor lock → current policy evaluate → master / PO / duplicate / domain checks
  DENY / ESCALATE → audit + existing controller flow, zero signing or network
  ALLOW → persist payment reservation
    x402 adapter → re-read current policy, PO, history and approved master wallet
      GET demo vendor /invoices/:id → 402 PAYMENT-REQUIRED
      validate exact chain, token, amount, recipient, resource and EIP-712 domain
      recheck policy/master → Keychain signer → PAYMENT-SIGNATURE retry
      vendor → public facilitator verify + settle → PAYMENT-RESPONSE
      audit hash → Base Sepolia Transfer + authorization nonce confirmation → paid
```

- `orchestrator/src/x402/index.ts` uses maintained `@x402/core` and `@x402/evm`
  2.28.0 with viem 2.57.10. Protocol encoding, signing, verification and
  settlement use SDK APIs, not a hand-rolled x402 protocol.
- `PayablesSeat` falls back to `process.env.PAYMENT_RAIL` when no explicit rail
  option is supplied. With `x402` on a non-macOS web host, the default Keychain
  signer raises internal `X402_REQUIRES_MACOS_KEYCHAIN`; otherwise allowed invoices
  hold safely. Web-host integration must account for that macOS-only signer.
- `PAYMENT_RAIL=x402` is the explicit server-side opt-in. Unset or `nessie`
  keeps the existing adapter. Unknown values fail closed. No mainnet flag,
  alternate asset, arbitrary RPC or payment-network setting exists.
- The approved master `accountId` must be
  `x402:eip155:84532:<approved EVM wallet address>`. The invoice's bank reference
  must match it. This reuses the existing opaque account-ID contract and does
  not introduce a model-controlled recipient field or change the database schema.
  Existing bank-only vendors remain held on the x402 rail.
- `InvoiceRecord.source` retains the trusted sender envelope for the adapter's
  fresh policy check. `SeatOptions.state.getPolicy` is optional for compatibility;
  production adapters should supply it. With it, the seat and signing boundary
  use the current saved policy; otherwise the existing bundled default applies.
- `PayablesSeat` accepts an injected `x402: PayablesClient` for tests or trusted
  bootstrap; otherwise the opt-in uses the CDP Keychain credentials (or explicit
  direct-key fallback) and the localhost vendor at
  `http://127.0.0.1:4027`. The root package exports `x402Payables` and its options.
  `vendorOrigin` is trusted server configuration, never extracted invoice data.
  HTTP is allowed only on loopback; redirects are refused.
- Policy ALLOW is required twice within the adapter and once at the seat. The
  rail also imposes the fixed $2,000 policy maximum even if an owner raises their
  general policy limit. A passkey exception never substitutes for ALLOW.
  Live signing additionally requires exactly one cent; larger amounts are only
  exercised by injected offline mocks.
- Challenge validation pins v2 / `exact` / `eip155:84532` / testnet USDC
  `0x036CbD53842c5426634e7929541eC2318f3dCF7e`, exact invoice cents converted
  to six-decimal units, master recipient, requested resource, and USDC v2
  EIP-712 domain. It rejects unsolicited extensions, Permit2 and other flows.
- `startTestnetVendor` in `x402/vendor.ts` is a loopback-only, independent demo
  endpoint. Its bootstrap-owned catalog returns 402 with the invoice amount.
  It verifies and settles through the SDK's `x402ResourceServer`. No voice
  tools, Nessie clients, reducers or policy rule IDs changed.
- `x402/console.ts` (`runX402Console`) drives the operator-console buttons with the
  same seat, adapter and vendor. Its **x402 simulated** rail injects an in-process
  mock facilitator (it checks the real EIP-3009 signature locally, then returns a
  random fake hash), an ephemeral payer key and a local transfer check. Audits use
  `x402_simulated_*` actions and `paymentRail: "x402 simulated"`; the adapter and
  vendor refuse that label without injected mocks. Console holds are not routed to
  the controller inbox: an x402 payment never takes a passkey exception.
- Policy blocks, attempts, fresh checks, settlement hashes, uncertain outcomes
  and replays go through `StateStore.appendAudit`. `SeatResult.paymentRail`
  supplies the display label; consumers must preserve it when showing receipts.
  Settlement hashes remain in the audit even if confirmation later fails.

## Run and verify

### In the app (operator console)

1. Start the host, for example offline:
   `DEMO_AGENTS=0 STATE_STORE=memory DEMO_TUNNEL=0 DEMO_PORT=3300 pnpm demo:up`.
2. Open `http://127.0.0.1:3300/operator` and press **Unlock local operator session**.
3. Under **Pay a vendor invoice with x402**:
   - **Pay vendor with x402 · SIMULATED** pays an approved $1,250.00 Acme Supply
     invoice in simulated USDC. The receipt shows the rail, `paid`, amount,
     vendor-master recipient, policy ALLOW, 1 signature and 2 vendor requests
     (402 challenge, then signed retry), a simulated hash and **Open payment
     audit**. No Keychain key, chain or internet is used.
   - **Try blocked x402 invoice · SIMULATED** submits $2,450.00, over the $2,000
     Payables limit. Policy returns ESCALATE `OVER_LIMIT`; the receipt shows
     `held`, 0 signatures and 0 vendor requests.
   - **Pay vendor with x402 · TESTNET** is disabled, with the reason shown, unless
     the host was started with `X402_LIVE=1` on macOS **and** the Keychain wallet
     exists and the CDP credentials (or explicit direct fallback) are configured.
     With those gates, it confirms first, prepares the selected wallet and checks it holds at least
     0.01 test USDC, pays a $0.01 invoice on Base Sepolia through the public
     facilitator, and links the basescan transaction. It is once per host process:
     another click replays the stored receipt (or the held result) and does not
     sign again. A host restart allows one new 0.01 test-USDC payment. This path
     records to the audit chain only; it never writes `docs/evidence/x402/live.json`.
4. Audit links open the existing audit wall, which still needs its operator code.

Browser responses contain only labels, public addresses, hashes, policy results
and audit IDs. The signer, Keychain read and facilitator calls stay on the host.

### CLI

Requires Node 22+, pnpm and macOS Keychain. Use the CDP one-shot command above
for new proof. The older command below targets the already-reserved historical
journal and refuses another payment:

```sh
pnpm install
pnpm --filter @backroom/orchestrator x402:wallet
# Fund the printed PAYER address at https://faucet.circle.com:
# USDC → Base Sepolia → payer address → Send 20 USDC.

pnpm --filter @backroom/orchestrator exec vitest run src/x402 src/payables src/vendor
pnpm --filter @backroom/orchestrator typecheck

# Explicitly opts into a real TESTNET payment only:
X402_LIVE=1 PAYMENT_RAIL=x402 pnpm --filter @backroom/orchestrator x402:live
```

The live script starts the vendor, seeds the approved wallet/PO, claims the
Payables task, executes the seat, saves public evidence and closes the vendor.
It has an exclusive `docs/evidence/x402/live.json` journal written **before**
payment: this repository already contains the successful run, so rerunning
refuses to pay again. Do not remove that journal to retry an uncertain payment.
A deliberately new demo run needs a separately reviewed new invoice and journal;
the supplied proof remains immutable. Unit tests use mocked network/facilitator
and chain receipts; the vendor test uses only local loopback HTTP.

The finance repository/vendor dedupe are single-process demo storage. Existing
Payables reservations prevent retries while that repository survives; the live
journal survives process exit. For deployment, keep the same durable
FinanceRepository and vendor lock across all writers, persist vendor settlement
claims, and reconcile ambiguous attempts before any retry. No durable
SpacetimeDB vendor-master rollout or controller passkey exception was exercised
by this proof. The operator console adds no approval route and no voice route.

## Historical x402 builder notes

- For the historical direct-key proof, Coinbase quickstarts led with CDP-managed wallets and API-key
  authentication. A self-custodied viem signer plus the public testnet
  facilitator needs neither; we verified `/supported` first instead of requesting
  an unnecessary key. A clearer keyless testnet path would shorten setup.
- The x402 repository moved to the Foundation; `coinbase/x402` points there and
  is now a development fork. We followed the maintained scoped SDK packages.
- The current client defaults to a $1 per-payment spend control. We explicitly
  set its cap to $2,000 while validating each challenge against the exact
  policy-approved invoice amount. This preserves both application and SDK caps.
- Browser faucet components rerender, invalidating accessibility references.
  Refreshing before each action and selecting Base Sepolia through its listbox
  worked; Circle's invisible reCAPTCHA required no manual challenge in this run.
- HTTP 200 and a facilitator hash are insufficient accounting evidence. We
  verify the chain, exact token Transfer and signed authorization nonce before
  claiming paid, and retain
  uncertainty rather than generating a second authorization after an RPC error.
